# Week 18: MFA, recovery codes, and passkeys

## Goal

Add a library-backed TOTP second factor with replay/rate-limit controls, then design a passkey integration precisely enough to explain its phishing resistance without implementing WebAuthn cryptography yourself.

Time budget: 8-12 hours for TOTP plus the passkey design exercise.

## Start here

Begin with the completed Week 17 application:

```bash
mkdir -p week-18/notes week-18/var
cp -R week-17/src week-17/tests week-17/tools week-17/Makefile week-17/schema.sql week-17/Caddyfile week-18/
make -C week-18 clean all test
```

Your starting system supports local passwords and OIDC, then creates ordinary local sessions. MFA changes when that session may be issued; passkeys change the primary authentication evidence itself.

Install a mature TOTP implementation such as OATH Toolkit:

```bash
brew install oath-toolkit pkg-config
oathtool --version
pkg-config --modversion liboath
```

Use the library's verification API. Do not implement HMAC or truncate its output yourself.

## Milestone 1: Model TOTP enrollment state

One suitable fresh-schema design is:

```sql
CREATE TABLE IF NOT EXISTS totp_credentials (
  user_id INTEGER PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  secret_nonce BLOB NOT NULL,
  encrypted_secret BLOB NOT NULL,
  created_at INTEGER NOT NULL,
  enabled_at INTEGER,
  last_accepted_step INTEGER,
  CHECK (last_accepted_step IS NULL OR enabled_at IS NOT NULL)
);

CREATE TABLE IF NOT EXISTS recovery_codes (
  id INTEGER PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  code_hash TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  used_at INTEGER,
  UNIQUE (user_id, code_hash)
);

CREATE INDEX IF NOT EXISTS recovery_codes_user_idx
  ON recovery_codes(user_id);

CREATE TABLE IF NOT EXISTS mfa_challenges (
  challenge_id TEXT PRIMARY KEY,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  created_at INTEGER NOT NULL,
  expires_at INTEGER NOT NULL,
  attempts INTEGER NOT NULL DEFAULT 0 CHECK (attempts >= 0),
  consumed_at INTEGER
);

CREATE INDEX IF NOT EXISTS mfa_challenges_user_idx
  ON mfa_challenges(user_id);
```

A TOTP verifier must recover the shared secret, so a one-way password hash cannot store it. For this local lab, encrypt it with libsodium's authenticated secret-key encryption, storing the ciphertext and its unique nonce in the columns above, and load the master key from a permission-restricted file/environment outside the repository. Document that production key management is a separate hard problem. Never log or commit the secret/master key.

Store recovery codes only as digests of high-entropy random values. Generate several, display them once at enrollment, and make each single-use.

## Milestone 2: Enroll with re-authentication

Implement authenticated, CSRF-protected enrollment:

1. Require the current password again for a local-password user, or a recent OIDC authentication according to an explicit policy.
2. Generate a random TOTP secret through approved random APIs.
3. Construct an `otpauth://totp/...` URI with correct issuer/account percent-encoding.
4. Display the URI or a QR generated by a maintained library/tool; never write it to logs.
5. Keep the credential pending until the user supplies one valid current code.
6. On confirmation, enable TOTP and show newly generated recovery codes exactly once.

Require HTTPS and `Cache-Control: no-store`. Cancelled/expired enrollment must delete pending secret material.

Use a 30-second step and six digits only if those match the library/provider configuration you test. Accept a narrow clock window, such as one adjacent step, and record the usability/replay trade-off.

## Milestone 3: Split password and session issuance

For a TOTP-enabled account, correct username/password is not yet full authentication:

```text
password succeeds
-> create short-lived one-use MFA challenge
-> set restricted challenge cookie
-> POST /mfa/verify with code + CSRF/challenge binding
-> verify TOTP and replay/rate policy
-> consume challenge
-> create full ordinary session
```

Do not create the full session before the second factor succeeds. The challenge must reveal no reusable password proof, expire within minutes, allow few attempts, and be unrelated to a normal session ID.

After accepting a TOTP code, atomically store its time step and reject the same/older step for that user. Rate-limit guesses by account/challenge/source IP. Six decimal digits have little entropy; rate limits and one-use challenges are essential.

Offer a recovery-code path that consumes exactly one matching unused digest in a transaction. A recovery code is an authentication credential, not a convenience string.

## Milestone 4: Test loss and reset policy

Document who can disable/reset MFA. A logged-in browser alone may be a stolen session; require recent re-authentication and CSRF protection. Password reset should not silently disable MFA unless your recovery policy explicitly treats email reset as sufficient for the whole account.

Test:

- enrollment cannot complete without a valid initial code;
- password alone creates no full session when TOTP is enabled;
- valid current code creates one session;
- wrong/expired/replayed code fails;
- challenge expiry, attempt limit, and replay all fail;
- adjacent clock-step policy behaves exactly as documented;
- one recovery code works once and another remains unused;
- logs/database expose neither plaintext TOTP secret nor recovery codes;
- MFA disable requires recent primary authentication and CSRF;
- OIDC accounts follow the explicitly chosen upstream/local MFA policy.

Use an injected clock; do not wait for real 30-second boundaries in automated tests.

## Passkey design lab

Do not write a WebAuthn parser or signature implementation. Read the WebAuthn concepts and design integration around a maintained server library (for example, an appropriate libfido2/WebAuthn component) plus the browser's `navigator.credentials` API.

In `notes/passkey-design.md`, specify two ceremonies.

### Registration

```text
server creates random one-use challenge tied to user/session
-> browser calls navigator.credentials.create with RP ID and origin context
-> authenticator creates credential key pair
-> browser returns credential ID + attestation/client data
-> server library verifies challenge, type, origin, RP ID, and attestation policy
-> server stores credential ID, public key, sign counter/metadata
```

### Authentication

```text
server creates random one-use challenge
-> browser calls navigator.credentials.get
-> authenticator signs bound ceremony data
-> server library verifies challenge, type, origin, RP ID, signature, user verification, and counter policy
-> server creates ordinary local session
```

For every arrow, label attacker-controlled inputs, maximum sizes, expiry, and replay behavior. Specify exact HTTPS origin and RP ID; these bindings are central to phishing resistance.

Compare evidence:

| Method   | Server stores              | Client proves                                  | Main phishing property                   |
| -------- | -------------------------- | ---------------------------------------------- | ---------------------------------------- |
| password | expensive verifier         | knowledge of reusable secret                   | user can submit it to wrong origin       |
| TOTP     | recoverable shared secret  | current short code                             | code can be relayed in real time         |
| passkey  | public key + credential ID | signature by private key for RP-bound ceremony | authenticator enforces RP/origin binding |

Passkeys still require account recovery, device synchronization/loss policy, credential management, and secure session handling after login.

## Optional WebAuthn spike

Only after the design is complete, add provider/library-backed registration and authentication behind feature flags. Keep it optional because correct attestation/authenticator-data parsing is larger than this course's core C server.

Acceptance for the spike must include wrong challenge, wrong origin, wrong RP ID, modified signature, replayed assertion, unknown credential ID, and user-verification-policy failures. A successful assertion should create the same local opaque session, not a new parallel authorization system.

## End-of-week working state

At the end of Week 18, a TOTP-enabled local account receives no full session until a rate-limited, one-use MFA challenge accepts a non-replayed library-verified code or unused recovery code. Secrets are encrypted/digested appropriately. The passkey document specifies complete RP-bound registration/authentication ceremonies and library validation responsibilities.

Verify:

```bash
make -C week-18 clean all test
sh week-18/tests/test_totp.sh
```

The TOTP test must include password-only denial, valid-code success, replay denial, throttling, and single-use recovery. Review `notes/passkey-design.md` by answering why a signature valid for an attacker's RP does not authenticate the victim to authlab. This is the completed 18-week implementation baseline for the final audit.
